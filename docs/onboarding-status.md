## Safety and consistency behavior

- The old case simulator remains usable in databases where onboarding has not started. Starting onboarding permanently puts that database into this release's T0 path, revokes unused permits, and refuses to start if actions are still running or unresolved. Use a separate `--data` directory to retain an independent action lab.
- The administrator configures; gate owners sign using separate authenticated role tokens. Request bodies cannot supply their own trusted actor or role. Local tokens are simulation identities, not SSO or MFA.
- Saving any configuration clears signatures and returns shadow mode to setup. API edits and signatures reject stale configuration revisions.
- Probe results expire after five minutes. Expired evidence blocks telemetry readiness and holds shadow readiness. Re-probing invalidates inventory/telemetry signatures; owners must review the updated evidence. There is no background production monitoring worker in this release.
- Unknown devices and mismatched inventory cannot enter the onboarding monitoring path. The service checks identity/inventory gates, current read-only probe, asset and source before ingesting an observation.
- Configuration accepts vault references and rejects common secret-bearing fields. Never paste actual credentials into descriptive fields; this is not a general secret-scanning service.
- Beginning onboarding disables action permits and execution in the service layer, including previously issued permits. Changing UI state or calling the API directly cannot bypass T0. Starting shadow does not enable external writes.
- Synthetic seven-day coverage, SSO/SCIM/MFA checks, connector certifications, policy replay and AI pilot evidence never establish enterprise readiness.

## Open the workflow

The current local runtime uses `http://127.0.0.1:8080` and `/tmp/hardware-overwatch-runtime/demo-credentials.json`.

1. Connect with the `policy_admin` token and choose **Onboarding**.
2. Click **Start onboarding at T0**, then expand **Configure onboarding** and click **Load simulation configuration**. This creates test inputs only; no signatures are added.
3. Disconnect and connect with `iam_lead`. Accept the identity request and sign the identity gate. That owner can also sign its part of the connectors gate.
4. Connect as `operator`, run **Probe declared lab device**, and inspect the inventory and read-only result. The probe only contacts the configured loopback simulator; it does not scan your network.
5. Each listed owner signs their gates. `infrastructure_lead` signs inventory; `operator` and `security_lead` sign telemetry; all seven connector owner roles sign connectors; `risk_lead` and `security_lead` sign policy. AI is optional and disabled in the sample.
6. As `risk_lead`, start simulated shadow mode. All actions remain T0. Review the separate production blockers panel.

The refreshed credential file preserves existing role tokens and adds the onboarding owner roles. No credentials are stored in source control. Runtime data under `/tmp` is temporary and may be removed at reboot.
